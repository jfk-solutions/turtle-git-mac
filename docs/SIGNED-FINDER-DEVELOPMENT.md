# Signed Finder development

Finder badges and menus require the app, extension and cache service to share an
authorized App Group. An unsigned build cannot prove this integration. TurtleGit
uses the macOS group name `$(TeamIdentifierPrefix)org.turtlegit.macos`, expanded
with the selected Apple developer team. The three peers receive the same group;
the cache Mach service appends `.cache` to that name.

Apple permits this macOS team-qualified namespace without listing the group in a
provisioning profile. Its registered `group.` namespace follows different profile
rules. See [Apple's App Group container guidance](https://developer.apple.com/documentation/xcode/accessing-app-group-containers).
Runtime lookup derives the team from the actual code signature and verifies the
task's group entitlement before requesting a container. Unsigned/ad-hoc processes
refuse access. The authenticated XPC requirement still pins Apple's signature
anchor, the same team and the exact app/helper identifiers.

## Build a development candidate

Select your real Apple developer team in Xcode. Alternatively, use the shared
App Store scheme with an installed Apple Development identity:

```bash
xcodebuild -project TurtleGitMac.xcodeproj -scheme TurtleGitAppStore \
  -configuration AppStore -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath build/signed-development -allowProvisioningUpdates \
  DEVELOPMENT_TEAM=YOUR_TEAM_ID CODE_SIGN_IDENTITY='Apple Development' build
```

Replace `YOUR_TEAM_ID` with your team's identifier. Xcode may create or update its
managed development profiles for the app, Finder extension and cache service.
Development profiles can expire; this candidate is not an App Store export or a
notarized Developer ID release. Distribution signing, licensing clearance and
submission remain separate release requirements.

The launch-agent embedding phase expands the service name using the same build
team without changing the already signed helper. Do not hand-edit only one peer's
entitlement or leave the literal build-variable text in the packaged agent plist.
A build with no team gets an unqualified diagnostic service name; it does not
acquire App Group access.

## Check actual sandbox execution

After building, run the signed-runtime check with the explicit SHA-1 of your
installed development identity, as listed by `security find-identity -v -p codesigning`:

```bash
python3 scripts/test-signed-finder-runtime.py \
  build/signed-development/Build/Products/AppStore/TurtleGitMac.app \
  --team YOUR_TEAM_ID --identity YOUR_IDENTITY_SHA1 \
  --report build/qa/signed-finder-runtime.json
```

The check first verifies actual Apple signatures, peer teams, sandbox/group
entitlements, the generated service name and inherited sandbox signing on the
packaged Git executable. It then creates disposable copies with unique QA bundle
identifiers. These run directly as sandboxed processes, without registering a
Finder extension or background job. A writer runs the packaged inherited-sandbox Lexilla helper and Git and publishes
a private fixture snapshot. A separate reader verifies its content. A negative
process without the group entitlement must fail to read that snapshot.

The check removes only its UUID-named fixture directory through an entitled
process and reaps its processes. The shipping candidate stays unchanged. It does
not certify installed Finder activation, live overlays, multi-selection menus,
background-service registration, external repository bookmarks, Keychain/SSH or
network transport. Those require the corresponding signed installed workflows.

Switching developer teams changes the App Group namespace. Shared cache and menu
presentation files are regenerated by the app; do not move permission bookmarks
or credentials into the group to work around a missing entitlement. Private grant
stores remain separate from Finder's status data.


Inherited-sandbox helpers cannot be launched by an ordinary unsandboxed build
script. Embedding runs functional checks on the verified source payload before
signing, then audits the signed copy's bytes, architecture, linkage and exact
inheritance entitlements. The signed sandbox probe supplies the real parent for
Lexilla's version check and Git's repository operations.
